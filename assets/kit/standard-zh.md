# AI Friendly 标准 v0.1

**状态：** 公开草案 · **发布：** 2026 年 11 月 15 日 · **许可：** CC BY 4.0
**规范网址：** https://aifriendly.fyi/zh/standard/

> 一套开放、可实践的标准，适合希望与 AI 智能体协作的网站和服务——同时不放弃对内容、数据和用户的控制。

## 这是什么
AI Friendly 标准描述“对 AI 友好”在实践中意味着什么。它不是判断内容是否由 AI 生成的测试，而是一份清单：当 AI 智能体——或使用智能体的人——到来时，让网站或服务可读、可操作、可安全使用。

它分为三个等级，每个等级都可以独立使用。第 1 级关心“能不能被读”，第 2 级关心“能不能被用”，第 3 级关心“能不能被托付行动”。

标准刻意保持技术中立。它引用已有的格式与规范——robots.txt（RFC 9309）、sitemap.xml、schema.org、OpenAPI、RFC 9457、security.txt（RFC 9116）、WCAG 2.2——并把 llms.txt、MCP 等新兴方案列为“有用时推荐”，而不是强制。

它不要求你把内容送出去。一个服务可以拒绝所有 AI 爬虫，同时仍然完全 AI 友好。重要的是政策明确、条款可读、智能体不会误入你从未授予的权限。

## 原则
1. **声明，而不是漂移** — 清楚的政策好过意外的政策。允许或拒绝都可以，但要写出来。
2. **可读优先** — 如果机器读不到页面，其他都无从谈起。
3. **同意是架构的一部分** — 开放不是许可。智能体只能在明确声明的作用域内行动。
4. **钥匙在人手里** — 不可逆、破坏性或付费操作必须由人决定。
5. **同一个网络，两类读者** — 无障碍与机器可读做的是同一件事。
6. **不做认证表演** — 自动化检查是证据，不是证明。认证意味着经过审核。

## 第 1 级 — 可读

基础层。不需要特殊 API、不需要智能体集成、不需要新协议。只需要一个说清楚自己是什么的网页，让人类和解析器都能跟上。

### R1. 主内容由服务端渲染

主要文字与链接直接出现在 HTML 响应中，而不是只靠客户端 JavaScript 拼装。

**为什么.** 许多智能体和爬虫只抓取 HTML，不运行浏览器。如果内容只在 JavaScript 执行后出现，它们就看不见你。

**如何检查.** 关闭 JavaScript，或用 curl 抓取页面，检查标题和正文是否在响应里。如果不在，请加入服务端渲染、静态生成或预渲染。有些网站还会通过 Accept: text/markdown 做内容协商；这是加分项，不是必需项。

### R2. 语义化结构与标题层级

一个清晰的 H1、合理的标题顺序，以及 header、nav、main、footer 等语义地标。

**为什么.** 结构让模型知道什么是标题、章节、菜单和脚注。一个字体很大的 div 并不携带这些含义。

**如何检查.** 关闭 CSS，页面仍应按合理顺序阅读。检查每页只有一个 h1、没有跳级标题，并使用了 main、nav、header、footer。

### R3. 唯一的标题与描述

每个页面都有唯一、具体的 title，以及概括本页内容的 meta description，而不是只写品牌名。

**为什么.** 标题和描述是搜索、浏览与智能体工具最常使用的摘要字段。

**如何检查.** 检查文档 head。它们应在全站唯一，并且不看 URL 也能识别页面。

### R4. 规范链接与稳定永久地址

页面声明规范 URL，并使用稳定、人类可读的地址。

**为什么.** 重复 URL 会分散信号，频繁改地址会破坏引用。智能体会缓存并引用它找到的东西。

**如何检查.** 检查 link rel=canonical 是否指向首选地址。旧地址应 301 跳转，而不是直接消失。

### R5. robots.txt 与 XML 站点地图

根目录有 robots.txt，并提供列出规范页面的站点地图。

**为什么.** robots.txt 是声明爬虫规则的标准方式（RFC 9309）。站点地图让发现页面变得确定。

**如何检查.** 抓取 /robots.txt，确认它引用了站点地图；再抓取站点地图，检查 XML 是否有效、URL 是否为规范地址。

### R6. 明确的 AI 爬虫政策

robots.txt 明确写出你允许或拒绝的 AI 智能体，而不是只依赖通配符。

**为什么.** 不同厂商使用不同 user agent。点名写出它们，意图才可审计。明确拒绝是有效的；沉默不是政策。

**如何检查.** 为你关心的智能体添加 User-agent 分组，并写 Allow 或 Disallow。保持文件有效，并公开解释你的立场。robots.txt 被广泛遵守，但不是法律强制。

### R7. 结构化数据

用 JSON-LD 描述组织、页面及页面上的事物（Article、Product、Event、FAQ、BreadcrumbList），词汇来自 schema.org。

**为什么.** 它把“谁发布、这是什么、多少钱”变成有类型的事实，而不是猜测。

**如何检查.** 用 Schema Markup Validator 或 Google Rich Results Test 校验。只使用页面真实存在且可见的属性。

### R8. 媒体的文本替代

图片有有用的 alt 文本；视频有字幕；音频有文字稿；图表有文字摘要。

**为什么.** 屏幕阅读器和模型都会读取 alt。装饰图片应使用空 alt，而不是文件名。

**如何检查.** 检查每张有意义的图片都有 alt，每个视频都有字幕，每个音频都有文字稿。

### R9. 公开内容不设墙

面向公众发布的内容，无需登录、Cookie 墙、订阅弹窗或安装 App 即可访问。

**为什么.** 无论访客是人还是智能体，墙就是墙。内容若是公开的，就让它真正公开。

**如何检查.** 在干净会话中抓取 URL。如果弹窗或跳转挡住内容，它就不可读。若内容有意设为私有，请明确说明并不要放进公开索引。

### R10. 语言、字符集与链接预览

页面声明语言与字符集，并提供 Open Graph metadata，让链接预览干净可靠。

**为什么.** 语言和字符集防止乱码；OG 标签让链接在分享或摘要时更易读。

**如何检查.** 检查 html lang、meta charset、og:title、og:description、og:image（1200×630）和 og:url。

## 第 2 级 — 可操作

只有可读还不够。这一级要求你发布一份契约：能做什么、谁能做、价格是多少、限制是什么、失败时会发生什么。

### A1. 公开的机器可读接口

发布有文档的 API；至少为你希望机器使用的内容提供结构化 feed（JSON、RSS、Atom）。

**为什么.** 抓取 HTML 很脆弱。feed 或 API 才是一份契约。

**如何检查.** 记录端点、认证和限制，并确认它返回结构稳定、可解析的数据。

### A2. 标准 API 描述

用标准格式描述 API——OpenAPI 3.1、GraphQL schema 或公开的 MCP 工具清单——并放在稳定 URL。

**为什么.** 智能体可以发现能做什么，而不必逆向你的 JavaScript。

**如何检查.** 从文档和 /llms.txt 链接该描述。用 linter 校验 OpenAPI 文件。

### A3. 机器可读的价格与可用性

公开价格、套餐、限制与可用性以文本或结构化数据呈现，而不是只放在图片或销售电话里。

**为什么.** 智能体无法引用它读不到的价格。不透明的定价会迫使人来接手。

**如何检查.** 用纯文本发布定价页，并在合适时使用 schema.org Offer 或 PriceSpecification。

### A4. 稳定标识符与版本管理

资源有稳定 ID；API 有版本；弃用有公开时间表。

**为什么.** 智能体会保存引用。无声的破坏性变更会把自动化变成事故。

**如何检查.** 使用 /v1/ 之类的版本前缀、不可变 ID，以及带弃用日期的 changelog。

### A5. 智能体可用的认证

支持 API key 或带作用域令牌的 OAuth 2.0。不要让机器操作只能通过浏览器流程完成。

**为什么.** 如果唯一入口是人类点击 UI，这个服务就谈不上可操作。

**如何检查.** 记录令牌流程、作用域和有效期。公共客户端使用 PKCE。不要把长期密钥放进客户端代码。

### A6. 速率限制与标准错误

公开速率限制，并返回机器可读的错误，最好是 RFC 9457 problem details。

**为什么.** 智能体需要智能退避，并向用户解释失败原因。

**如何检查.** 记录限制与 429 行为。返回 application/problem+json，包含 type、title、status、detail。

### A7. 智能体问题反馈渠道

为智能体相关问题、滥用举报和访问咨询提供明确的联系人或页面。

**为什么.** 当智能体做错事时，人类需要一条找到人类的路径。

**如何检查.** 发布 /agents 页面，写明预期与响应时间，并提供一个可用的域名邮箱地址。

## 第 3 级 — 智能体可用

风险主要在这里。在网络上行动意味着花钱、改数据、发消息、删东西。这里的检查关于刹车、回执和退出。

### G1. 工具清单或 MCP 服务

发布机器可发现的工具清单——例如 MCP 服务——列出能力、输入和限制。

**为什么.** 清单把网站变成智能体能正确调用的工具，而不是让它猜 UI 自动化。

**如何检查.** 记录服务 URL、传输方式、认证、工具和调用示例，并给清单做版本管理。

### G2. 最小权限与人工确认

智能体只获得最低限度的作用域。破坏性、不可逆或付费操作必须得到明确的人工确认。

**为什么.** 没有刹车的自主性是负债。确认就是刹车。

**如何检查.** 区分读写作用域。支付、删除和权限变更都要重新确认，并明确说明后果。

### G3. 用户可见的审计日志

用户可以看到智能体做了什么、何时做的、代表谁做的。

**为什么.** 信任需要回执。审计轨迹让错误可发现、可挽回。

**如何检查.** 记录行为者、动作、目标、时间和结果，在账户界面展示，并允许导出。

### G4. 导出与删除

用户可以在明确时限内以程序化方式导出数据并请求删除。

**为什么.** 可携带与可退出是同意的一部分，也正成为越来越多地区的法律要求。

**如何检查.** 记录端点或流程、格式、时限和确认方式。

### G5. 来源与 AI 披露

当 AI 实质参与内容生产时，明确披露。媒体内容可在合适时使用 C2PA 等来源标准。

**为什么.** 人和智能体都需要知道自己在看什么。披露不等于检测。

**如何检查.** 在内容附近做清晰披露，保留 C2PA 清单，不要声称无法证明的人类作者身份。

### G6. 安全基线

全站 TLS、/.well-known/security.txt、客户端无密钥、输入校验，以及漏洞披露渠道。

**为什么.** 面向智能体的服务就是攻击面。基础卫生是前提，不是加分项。

**如何检查.** 发布 security.txt（RFC 9116），扫描依赖，轮换密钥，并测试授权边界。

### G7. WCAG 2.2 AA

公开体验达到 WCAG 2.2 AA。

**为什么.** 机器可读与人类可访问共享同一套基础：结构、标签、替代文本和可预测的行为。

**如何检查.** 用纯键盘、屏幕阅读器和自动化检查做审计，并修复自动化漏掉的人工问题。

## 如何声明

### 使用徽章

*自我声明 / 免费*

下载标志，用在网站或产品上，并写明你达到的等级。无需申请、无需付费、无需许可。你对声明负责。

### 申请审核

*认证 / Beta*

认证徽章面向能提供证据的服务：完成的自检、公开 API 或工具清单，以及第 3 级的安全检查。由人审核，并每年复核。

诚实说明。自我声明徽章是一种声明，不是审计。我们不会检查每一个展示它的网站。只有认证徽章经过审核，也只有认证徽章可以写“verified”。如果你看到认证徽章被用在没有公开列表的地方，告诉我们。
